# Friction log — SIGRID/CENEPRED public surface recon

Date: 2026-08-18

- **`curl` shadowed by an unrelated shell alias in some Bash calls, silently.** Multiple commands failed with `command not found: curl` inside a `for` loop even though `curl` worked fine seconds earlier in the same session. Root cause not fully diagnosed — likely a zsh function/alias that only triggers in certain loop constructs. Fix applied: prefixing every call with `command curl` made it reliable again. Cost: two wasted round-trips before switching to `command curl` as the default. Suggested playbook note: default to `command curl` (or an absolute path) in any repeated-call loop, not just when a failure is observed.

- **Assumed `datosabiertos.gob.pe` runs CKAN because of the `/dataset/{slug}` URL shape.** It's actually Drupal. `GET /api/3/action/package_search` returns a normal Drupal 404 HTML page, not a CKAN JSON 404 — easy to misread as "the CKAN endpoint exists but query failed" when it's really "this isn't CKAN at all". Caught it by reading the raw body instead of trusting the HTTP status alone. Lesson for the skill: when a government portal's URL shape looks like a known framework (CKAN, GeoNode, etc.), read the actual error body once before building more calls on that assumption — a 404 in JSON and a 404 in HTML mean different things.

- **`www.datosabiertos.gob.pe` returns HTTP 418 with a CloudWAF block page (Chinese-language, "访问被拦截") when the User-Agent isn't a browser string.** curl's default UA got blocked on `/api/3/action/*` paths specifically, while plain page requests without a UA override worked fine on some paths and not others — inconsistent enough that it cost a few cycles figuring out it was UA-based, not IP-based or a real API 404. Fix: always send a Chrome UA string against this host. Worth adding to the WAF/anti-bot reference if this pattern recurs on other `.gob.pe` hosts.

- **The ArcGIS Online item found via `REDES/E030/MapServer/5` (owner `fariasaz`, from the AGOL search results) was stale/wrong.** The actual `MapServer` only has layers 0-3; layer 5 returns a clean 404. This is exactly the kind of second-hand reference that would have gone straight into a client if not verified directly against the live service — AGOL search result metadata (title, url) is not authoritative for what a service currently exposes. No fix needed beyond what the skill already prescribes ("every claim is observed") — this is a good concrete example to cite for why layer IDs specifically need re-verification even when the base service URL is confirmed live.

- **agent-browser click on "ACCEDER AL VISOR DE MAPAS" did not produce a URL change or any captured `arcgis` network traffic**, despite the skill's own core-loop guidance being followed (snapshot, dismiss the modal first per the screenshot rule, then click). Possibly a new-tab open not captured by the active session, or a decorative duplicate link matched by `find text`. Did not chase further given time budget — logged as "needs verification" in the report rather than guessing. If this recurs, the fix is probably `click @eN --new-tab` explicitly plus checking for a second tab, rather than `find text` blind-clicking.

- **A second, independent recon session had already written `recon/cismid-igp-sources.md` into the same directory before this session finished**, covering overlapping ground (IGP, CISMID, licensing) but from a different angle (GeoServer WFS instead of ArcGIS REST) and with a stronger licensing finding (`Fees:NONE`/`AccessConstraints:NONE` on IGP's WFS `GetCapabilities`). Discovered it only by listing the directory near the end of the session, not before starting. Cost: no wasted probing (the overlap was on different endpoints so nothing was duplicated work), but it easily could have been — the assignment scoped a specific `.md` filename but didn't ask to check for sibling recon in progress. Playbook note: if a recon lands in a shared directory, `ls`/`git status` that directory in Phase 0, not just at the end, in case another session's output changes what's still worth probing.

No other friction. The `499` vs `500` distinction (token-required vs not-found) held up cleanly across every probe and was the single most useful technique in this session — worth keeping as a standing pattern in the ArcGIS-specific playbook notes if one gets written.
